# Сенс-групи у словнику й тренуванні — дизайн

Дата: 2026-08-20 · Статус: чернетка на ревʼю власника
Контекст: аналіз проблеми «run» (однакові деталі в усіх варіантів, сміттєві форми, стіна дублікатів у пошуку, «12 слів» при 4 картках) + рішення власника про групування перекладів одного сенсу.

## 1. Мета

Зробити одиницею словника і тренування **(слово + сенс)** замість (слово + переклад):
- у пошуку — один айтем на сенс із головним перекладом і розгорнутим списком «близьких за значенням»;
- у словнику — окрема картка на кожен збережений сенс з унікальними прикладами;
- у тренуванні — картка = сенс-запис; будь-який переклад сенсу вважається знанням сенсу.

Не-мета: фізичний мерж схем зберігання/синку (відхилено — конфліктує з D3/D11 і протоколом applySync); автозлиття старих записів без участі користувача; conceptKey у MVP (див. §8).

## 2. Модель даних (клієнт)

**Без міграцій.** Рядок `WordEntity` = сенс-запис:
- `translation` = **представник** групи (дефолт — primary сенсу; або синонім, який користувач явно обрав при збереженні);
- `detailsJson` = скоуплений блоб сенсу: дефініція, приклади сенсу, `senseKeys`, **повний список перекладів групи** (близькі за значенням), форми/IPA слова;
- дедуп при додаванні: пара **(source, сенс-група)** замість (source, translation) — той самий сенс двічі не зберігається; різні сенси одного слова — легальні окремі записи.
- fallback для рядків без `senseKeys` (легасі, ручні): ключ групи = source-текст (як зараз).

Знання (`knowledgePercent`, майбутні D10-поля `boxLevel`/`dueAt`/…) — на рядку, тобто на сенсі. Агрегація не потрібна.

## 3. Пошук (add-word flow)

- Клієнт групує відповідь `/v1/search` по `senseKeys` (усе потрібне вже в DTO); порядок у групі: `isPrimary` → `confidence`.
- Айтем списку: слово + головний переклад + дефініція/приклад сенсу. Кожен айтем — інший сенс, деталі не повторюються.
- Розгорнутий айтем: повні деталі сенсу + список «Близькі за значенням».
- ✓ на айтемі → зберігає сенс-запис із головним перекладом. ✓ на конкретному синонімі → зберігає той самий сенс-запис, але представник = обраний синонім.
- «Неякісний переклад» переоформити як явну дію-скаргу (іконка/кнопка), не текст-вирок.

## 4. Список словника

- Картка = збережений сенс-запис: «run — бігти» і «run — пробіжка» поруч, кожна зі своїм сенсом і своїми прикладами.
- Розгорнута картка: деталі сенсу + «Близькі за значенням» з групи.
- Лічильник заголовка = кількість записів (стає чесним автоматично).
- Легасі-рядки (по-перекладні) показуються через **похідне групування** по (source + senseKey, fallback source) — без деструктивної міграції; чистка дублікатів = звичайне видалення (D3 soft-delete, протокол синку без змін).

## 5. Тренування

- Картка = рядок = сенс-запис (як і зараз технічно): фронт — слово + приклад сенсу; зворот — представник + «також: близькі за значенням».
- Бінарна оцінка пише ±дельту в один рядок. Жодних політик агрегації.
- Легасі-групи в колоді: похідне групування, відбір по min(knowledgePercent) групи.
- Контекстний режим: сенс-групи знімають обмеження «кластери синонімів виключені з тренування» (ContextPractice `senseRepresentatives`) — дистрактори й далі лише з інших сенсів.

## 6. Передумови на gateway (без них групувати нема по чому)

1. Per-variant деталі: `visibleSenseIds` = `senseKeys` конкретного перекладу замість union напрямку (`lexicon.service.ts` enrichment); синоніми/антоніми sense-scoped.
2. Пріоритет curated: seed-import має перекривати translator-кеш при видачі; форензик dev-БД — чому промоутнуті рядки «run» знову translator (SQL у аналізі від 2026-08-20).
3. Фільтр сміттєвих форм у free-dictionary.provider (теги `table-tags`/`inflection-template`, тексти `no-table-tags`/`glossary`/`-`) + одноразовий cleanup `lexicon_word_forms`.

## 7. Скіли генерації перекладів (грумінг-імпрувмент, джерело істини ~/.codex/skills)

1. **Інваріант атомарності сенсу**: кожен переклад сенсу мусить природно перекладати прикладове речення цього сенсу; інакше — розщепити сенс. Заборона umbrella-глосів («…, or …»-переліки різних значень).
2. **Дедуп сенсів**: однаковий зміст + однакове прикладове речення → один сенс (один senseKey), переклади атрибутуються до нього.
3. **Primary на кожен сенс** (зараз — один на запис); ранжування близьких за confidence. Контракт/валідатор/імпортер це вже допускають (перевірено).
4. Перевірки у `validate_reviewed_batch.py`: «or»-списки в дефініціях, дублікати прикладів між сенсами, однакові нормалізовані дефініції, сенси без жодного перекладу.
5. Ті самі правила — у `vocabee-translate-v2-migration` (робить fullRecord-регенерацію) і `vocabee-secondary-translate`.
6. Донарізка верхівки частотного списку регенерацією (за статистикою: 77 % сенсів із ≥2 перекладами мають «or»-глоси; ~половина в контентних словах — справжні umbrella; 211 сенсів без перекладів).

## 8. Фаза 2 (опційно, за окремим рішенням власника): conceptKey

«run—бігти» + «run—пробіжка» (одна дія, різні POS/приклади) можуть групуватись у «сімейку» через опційний `conceptKey` на сенсі, який емітять скіли. Поза MVP: потребує розширення V2-контракту й даних.

## 9. Порядок фаз

0. Gateway-передумови (§6) — незалежні, дають ефект одразу.
1. Скіли (§7) + синк ~/.codex → ~/.claude.
2. Клієнт: пошук/додавання (§3) — групування, представник, новий дедуп.
3. Клієнт: список (§4) — картка на сенс, похідне групування легасі.
4. Клієнт: тренування (§5).
5. Дані: регенерація верхівки; форензик dev-БД.
6. Документація: нове D-рішення в `00-overview-and-decisions.md`, оновлення `10/11/13/14/17` з мітками [НОВЕ], edge-case «дублікати одного сенсу» в `10`.

## 10. Тестування

- Юніт: групування по senseKeys (з fallback і частковим перетином ключів), дедуп (source, sense), вибір представника, побудова колоди з легасі-групами (min-знання).
- Валідатор батчів: нові перевірки §7.4 на фікстурах (umbrella-глос, дубль-приклад, сенс без перекладів).
- Ручний прогін «run»: після gateway-фіксів + регенерації — пошук показує окремі сенси з унікальними прикладами; збереження двох сенсів = дві картки; колода без дублів фронту.

## Відомі ризики

- Неконсистентні `senseKeys` між рядками різних ревізій лексикону → групування має бути толерантним до часткового перетину ключів.
- Легасі-слова без деталей (`details == null`) → завжди fallback на source-групування.
- Поки dev-БД засмічена translator-кешем, нові збереження успадковують порожні `senseKeys` — тому фаза 0 передує клієнтським фазам.
